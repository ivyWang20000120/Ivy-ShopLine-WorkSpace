# PRD Writer（产品需求文档写作规范）

本 skill 提取自一份真实、经过验证的电商保险应用 PRD（Shopline 保险应用），把其中稳定复用的**文档结构**和**写作范式**沉淀下来，供以后撰写同类型 PRD（尤其是"多角色后台 + C端组件 + 第三方接口对接 + 状态机 + 财务流水"型产品）时直接套用，无需每次重新上传原文件。

## 使用方式

1. 先向用户确认（如果信息不全，用一轮提问补齐，不要连续追问超过3个问题）：
   - 产品/应用名称，一句话概括产品范围
   - 涉及几个"端"：例如商家端后台、平台运营后台、C端前台组件、系统定时任务
   - 核心角色及其权限边界
   - 涉及的外部系统/第三方接口（支付、物流、保险公司、风控等）
   - 是否涉及资金流水（充值、扣款、退款、返佣、对账）
2. 按照下方【章节结构】逐节生成内容，**结构和小标题层级严格照抄**，只替换具体业务内容。
3. 每个功能点必须同时写"规则"（业务逻辑约束）和"验收"（可核对的验收标准），不要只写其中一项。
4. 涉及列表/清单类功能时，补充"字段建议"清单和"操作"清单（如适用）。
5. 文档末尾固定包含【状态定义】章节（用表格列出各类业务对象的状态机）和【非功能要求】章节。
6. 完整模板骨架见 `references/template.md`，可直接复制后填充。写作细节规范见下方【写作范式】。

## 章节结构（固定骨架）

```
# {产品名} PRD

## 1. 产品范围
用 1 段话说明本应用包含哪几个"端"/子系统，以及每一端的核心用途（一句话概括，不展开）。
再用一段话补充：前台组件、Webhook 处理、第三方接口对接范围（如物流查询、支付、投保/理赔类接口）。

## 2. 角色
用表格列出：角色 | 权限范围
角色通常包括：面向商家/客户的角色、面向平台运营的角色、C端最终用户角色、系统任务（定时任务/自动化角色）。

## 3. {端A，如"商家应用后台"}功能
### 3.1 ~ 3.N 按功能模块编号
每个功能模块固定包含以下小节（按需取舍，非强制全部出现）：
- 一段话说明该功能是什么
- "规则："bullet list —— 业务逻辑约束、边界条件、异常处理
- "字段建议："bullet list —— 列表页/详情页展示字段
- 操作说明（如按钮、跳转、触发条件）
- "验收："bullet list —— 可核对的验收标准，与"规则"一一对应

## 4. {前台/C端组件}
### 4.1 展示位置
### 4.2 交互规则 + 验收

## 5. {核心业务流程A，如订单与扣款流程}
按子流程分节，每节仍是"规则+验收"范式。

## 6. {核心业务流程B，如发货/物流/投保流程}

## 7. {核心业务流程C，如理赔与申诉流程}
适用于涉及"提交-审核-同意/拒绝-申诉"类多步骤审批流程。

## 8. {端B，如"独立管理后台"}功能
运营侧配置项、Dashboard、风险提醒、汇率/费率管理、异常处理、对账导出、定时任务类功能。

## 9. 状态定义
每个核心业务对象（如订单、保单、理赔）单独一个表格：状态 | 说明

## 10. 非功能要求
bullet list，通常包括：金额精度与可追溯性、Webhook幂等、第三方接口重试与错误记录、操作日志、
异步导出、防重复执行等。
```

## 写作范式（重要，务必遵守）

### "规则 + 验收"配对
- 这是本模板最核心的写作范式：**先讲清楚系统怎么运行（规则），再讲清楚怎么判断做对了（验收）**。
- "规则"描述的是系统行为/业务逻辑，用陈述句，一条一个点，不编号，用 `-` bullet。
- "验收"描述的是可核对的结果状态，通常以"XX后，YY应该ZZ"的因果句式呈现，方便测试同学直接转成用例。
- 验收条目数量不必与规则一一对应，但要覆盖规则中的关键分支（正常路径 + 至少1个异常/边界路径）。

### 表格的使用场景
- 角色权限、配置项说明、状态定义 → 用二列表格（左列是名称，右列是说明），不要写成段落。
- 清单类功能（如账单、流水、赔付记录）的展示字段 → 用"字段建议："bullet list，不用表格（因为字段多且是罗列，不需要第二列说明）。

### 金额/多币种类产品的固定套路
如果产品涉及跨境/多币种资金处理，固定补充：
- 统一结算币种是什么（如"统一按 USD 收取"）
- 折算汇率来源与加点规则（面向用户收费 vs 面向第三方对账，是否使用同一套汇率）
- 资金流水必须可追溯（增加/减少来源分别列出）
- 存在"钱包/账户余额"时，明确余额增加来源、减少来源，以及余额变化后是否触发自动扣款等联动逻辑

### 状态机的固定套路
- 每类业务对象（订单/保单/理赔单等）单独列状态表，字段为：状态 | 说明。
- 状态命名遵循"动词+结果"或"待+动词"模式，如：待付款、已付款、投保中、投保失败、已投保、已退保。
- 涉及审批类对象（如理赔）时，状态需覆盖：提交前 → 审核中 → 拒绝 → 可申诉一次 → 申诉终态 / 同意 → 执行中 → 完成，这条链路。

### 第三方接口对接类需求
- 明确本应用与第三方之间的处理维度是否与"对商户收费维度"不同（例如：对商家按订单收费，但对保险公司按包裹投保），这是容易被忽略但很关键的一点，务必显式写出。
- Webhook 处理需强调幂等性和重复通知（如重复扣款到账）的兜底方案。

### 语气与颗粒度
- 全文使用陈述句，不用"我们建议""可以考虑"等弱语气词。
- 功能点粒度以"一个可独立验收的行为"为单位拆分小节，不要把多个不相关规则堆在一个小节里。
- 编号统一用"X.Y"两级（章节.子功能），不出现三级数字编号，三级内容用无编号小标题或 bullet 表达。
